常见场景

  • 测试邮箱、日期、编号或简单标识符格式。
  • 从日志或文本中提取固定结构片段。
  • 检查分组和替换结果是否符合预期。
  • 排查斜杠、反斜杠和特殊字符转义。

使用建议

  1. 先准备 3 到 5 条应匹配和不应匹配的样例。
  2. 逐步增加规则复杂度，不要一开始写很长表达式。
  3. 确认是否需要忽略大小写、多行或全局匹配。
  4. 上线前在目标语言或目标系统中再测一次。

常见错误

  • 忘记转义点号、括号、方括号或反斜杠。
  • 贪婪匹配范围过大。
  • 把不同语言的正则语法混用。
  • 没有准备反例，导致规则过宽。

安全边界

复杂正则在大文本上可能导致性能问题。不要把未验证的复杂表达式直接用于生产系统或用户可控的大规模输入。

FAQ

为什么本页能匹配，代码里不匹配？

常见原因是目标语言的正则语法、转义层级、匹配标志或输入换行不同。

什么是贪婪匹配？

贪婪匹配会尽可能多地匹配内容，可能超过你预期的范围。需要时可使用更精确的边界或非贪婪写法。

正则适合解析 HTML 吗？

简单片段可以辅助处理，但复杂 HTML 应使用解析器而不是依赖正则。

深入工作流：正则测试必须同时准备正例和反例

正则表达式的危险在于它经常“看起来能用”。只用一个正确样本测试，很容易得到虚假的安全感。一个可靠的测试过程至少包含三类样本：应该匹配的正例、非常接近但不应该匹配的反例、以及空字符串、超长字符串、特殊符号等边界例。没有反例的正则，很可能在生产中匹配过宽。

使用 JavaScript 正则时，还要注意 flag 和字符串转义。g、i、m、s、u 会改变匹配方式；从测试器复制到代码时，反斜杠可能需要再转义一层。比如正则里的 \d 在 JS 字符串中常写成 \d。若这一点没有处理好，测试器里通过的表达式到了代码里可能完全不同。

操作前后的复核清单

  • 需要整串匹配时使用 ^ 和 $，否则子串命中也可能被当成通过。
  • 为每个规则保存正例和反例，后续改规则时一起回归。
  • 避免对不受控的超长输入使用复杂回溯模式。
  • 不要用正则承担完整 HTML、JSON、SQL 或自然语言解析任务。

真实排查案例

案例：一个订单号规则希望匹配 AB-1234，但表达式写成 [A-Z]{2}-\d{4}，没有加锚点。结果 xxxAB-1234yyy 也能命中。加上 ^ 和 $ 后，规则才表示整串必须符合格式。

建议的工具链

单个工具只能完成一个局部动作。更稳妥的方式是把相关页面串成检查链，先整理输入，再做转换或对比，最后保存结论。

何时不要只依赖在线工具

当输入包含生产密钥、客户数据、内部主机名、财务数据、法律文本或会影响线上系统的配置时，应使用团队批准的本地流程或受控环境。在线工具适合快速阅读、格式化、转换和辅助排查，但最终结论应回到源系统、接口文档、代码仓库或业务记录中确认。
